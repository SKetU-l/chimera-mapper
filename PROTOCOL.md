# Kreo Chimera V1 — configuration protocol

Reverse-engineered for interoperability by static analysis of Kreo's own
Windows configurator (`Kreo5.msi` → `GamingMouse.exe`, an OEM "Spirit of Gamer
G140" build), then verified command by command on a wired Chimera V1. Nothing
from the vendor software is redistributed here.

## Device

| | |
|---|---|
| Chip | Telink TLSR8278 (USB serial string) |
| Vendor ID | `0x248a` |
| Wired / 2.4G dongle / Bluetooth PID | `0x5b49` / `0x5b4a` / `0x8266` |

USB interfaces (wired):

| iface | collections | notes |
|---|---|---|
| 0 | mouse (report 1), consumer (2), system (3), vendor 32-byte in/out (5) | The mouse collection declares 3 button usages but 5 bits; bit 3 = back, bit 4 = forward. Linux ignores bits 3–4, which is why the side buttons need help. |
| 1 | vendor page `0xFF01`: report 7 — 32-byte input, 32-byte output, 7-byte feature | **Configuration channel.** |
| 2 | boot keyboard | Carries key bindings and macros generated by the firmware. |

## Framing

Every command is an 8-byte feature report on interface 1: `07 CMD p0 p1 p2 p3 p4 p5`.
No checksum, no sequence number.

* **Set:** `SET_REPORT(Feature) 07 CMD payload…`
* **Get:** `SET_REPORT(Feature) 07 (0x80|CMD) 00…`, wait ~10 ms, then
  `GET_REPORT(Feature)`. A valid reply echoes the query in byte 1; anything else
  is a stale buffer (the firmware ignores the requested report ID on GET).
* **Bulk data** (buttons, macros): a feature-report header, then 32-byte
  **output** reports (`07` + 32 bytes). These must go over the **control pipe**
  (`SET_REPORT(Output)`, `bmRequestType 0x21`, `wValue 0x0207`, `wIndex 1`). The
  firmware stalls output reports sent to the interrupt OUT endpoint (EP 6),
  which is where Linux hidraw routes both `write()` and `HIDIOCSOUTPUT`, so on
  Linux the interface is briefly detached and written through libusb.

### Sessions

The vendor tool brackets every apply with `F5` … `FA`:

* `07 F5` — begin.
* `07 FA` — **commit: writes flash and reboots the mouse.** It drops off USB and
  re-enumerates within about a second, so the transfer itself usually fails
  with a protocol error. Settings survive power cycles.

## Commands

| Cmd | Get | Payload | Verified |
|---|---|---|---|
| `01` polling rate | `81` | `[code]`, Hz = 1000/code (1, 2, 4, 8) | ✔ |
| `02` active DPI stage | `82` | `[stage, stage]`, 0-based. Applies instantly without a commit; the DPI button changes it too. | ✔ |
| `03` lighting mode | `83` | `[mode]` 0–5 (vendor names: off, neon, breathing, flash, lightshow, ambilight) | ✔ |
| `04` DPI table | `84` | 6 bytes, one per stage: `dpi/100 − 2` (200–10000, step 100) | ✔ (the vendor tool never reads `84`, but it works) |
| `05` button table | — | see below | ✔ |
| `06` rapid-fire interval | `86` | `u16 LE` of ms/10 | read ✔ |
| `07` macro upload | — | see below | ✔ |
| `F5` / `FA` | — | session begin / commit + reboot | ✔ |
| — | `89` | status: `[battery %, power, polling code, ?, ?]`; power `01` on battery, `02` charging. The percentage is a voltage estimate and reads high while charging. | ✔ (not used by the vendor tool) |

`85`, `87` and `8C`–`8F` do not answer; `88`, `8A` and `8B` answer with
values not yet understood. The vendor tool contains no firmware-update,
bootloader or factory-reset command; nothing else should be sent.

### Button table (`05`)

For packet `n` in 0..1: feature `07 05 02 n 20 00 00 00`, ~10 ms, then the
output report carrying bytes `32n..32n+31` of a 64-byte table. The table is 16
slots × 4 bytes; slots 0–5 are left, right, middle, back, forward, DPI.

| Binding | Bytes |
|---|---|
| keyboard | `00 <mods> <HID usage> 00`, mods: ctrl 01, shift 02, alt 04, gui 08 |
| mouse button | `01 00 F0+n 00` (F0 left … F3 back, F4 forward) |
| consumer | `03 00 <usage LE>` (CD play/pause, E9 vol+, …) |
| DPI up / down | `04 00 01 00` / `04 00 02 00` |
| DPI cycle | `07 00 01 00` |
| macro | `09 00 <slot> 00` |
| disabled | `00 00 00 00` |

Keyboard bindings are emitted by the firmware on interface 2, so they work on
every OS with no host software running.

### Macros (`07`)

For packet `n` in 0..8: feature `07 07 09 n 20 <slot> 00 00`, ~10 ms, then the
output report carrying bytes `32n..32n+31` of a 288-byte blob:

```
[slot] [mode] [repeat lo] [repeat hi]  then up to 71 four-byte events
```

* mode: `0` loop while held, `1` toggle (click starts, click stops), `2` run
  `repeat` times per click.
* key down `00 <usage> 00 00`, key up `80 <usage> 00 00`. Modifiers are usages
  `E0`–`E7`; mouse buttons are `F0`–`F4`.
* delay `<unit> 00 <ticks LE>`: unit `01` = 10 ms ticks, `0A` = 100 ms ticks;
  a delay as the very first event uses unit `04` (100 ms).

Re-send the button table in the same session after uploading a macro.

## 2.4G dongle

Same interface layout and commands; everything above works through the dongle
(verified: DPI table, active stage, polling rate incl. 1000 Hz, lighting,
button table, macros, battery). Differences:

* The dongle answers queries from a **cached copy** of the mouse's state that
  refreshes when the mouse talks to it (e.g. on movement), so reads can lag a
  write.
* `84` does not return the DPI table — the dongle echoes whatever table was
  last written through it, or `00 01 02 03 04 05`.
* The active stage (`02`) only reaches the mouse on commit.
* Commit (`FA`) does **not** reboot the dongle.
* Bulk packets need ~200 ms after each header and ~300 ms after each output
  report, or the dongle silently drops them while still acking the transfers.
* The dongle stalls its interrupt OUT endpoint; use the control pipe as wired.

## Lighting switch

The mouse has a three-position hardware lighting switch (plain light / RGB /
off). The `03` modes only apply in the RGB position, and there mode 0 falls
back to a default rainbow instead of turning the strip off. In that position
only modes 0 (rainbow) and 4 (lightshow) visibly play; 1, 2, 3 and 5 leave the
strip dark (5, "ambilight", presumably expects colours streamed from the host).
The behaviour in the plain-light position is untested.

## Bluetooth

A single HID interface: the mouse (report 3, declaring all **5** buttons, so
back/forward work natively) and a vendor collection (`0xFF01`) with a 4-byte
feature report 5. That report only echoes what was last written; no command
gets an answer, so the mouse **cannot be configured over Bluetooth**. Settings
written over the cable or dongle persist and apply here. Over BT, keyboard
bindings are not used — side buttons arrive as plain buttons 4/5.

The battery level is available from the standard GATT Battery Service
(BlueZ: `org.bluez.Battery1.Percentage`).

The GATT service `00010203-0405-0607-0809-0a0b0c0d1912` is Telink's standard
**OTA firmware-update** service. Leave it alone.

## Not yet explored
* Binding types `06`, `0A` (rapid fire), `0B` and the `07 00 02/03 00` variants.
* Per-stage DPI colours, LED colour/speed/brightness: the vendor tool has no
  commands for them.
